# KNOWN_ISSUES.md

## Open issues

### BLOCKER
- No database running locally — Prisma migrations and runtime require a PostgreSQL instance.

### MAJOR
- Production-grade execution isolation is not yet designed.
- Billing and metering are planned but not yet defined in detail.
- Final deployment topology is not yet confirmed.
- Prisma pinned to 6.x — Prisma 7.x requires config migration (prisma.config.ts + adapter pattern).
- Scheduler workers (webhook retry, run worker, schedule runner) are **disabled on Vercel** (serverless). They rely on setInterval loops that cannot run in ephemeral serverless functions. For production, use Vercel Cron Jobs or a dedicated background worker.
- Auth, workspace membership, and role middleware use VITEST bypass during tests — the full production auth + membership + role flow (token lookup → user resolution → membership check → role check) remains untested without a running PostgreSQL instance. The helper functions (getWorkspaceRole, assertWorkspaceMember) now have production-path coverage (no bypass).
- Route-level deny/allow tests for the last-owner guard (DELETE member → 400 when last owner), actor workspace cross-reference (PATCH/DELETE actor → 404 on workspaceId mismatch), actor ownership guard (PATCH/DELETE actor → 403 when non-owner MEMBER), storage ownership guard (DELETE dataset/KV/queue → 403 when non-owner MEMBER), and webhook ownership guard (PATCH/DELETE webhook → 403 when non-owner MEMBER) cannot be exercised at the HTTP level without a running PostgreSQL instance. Ownership logic (canUserManageActor) is unit-tested as a pure function without VITEST bypass; the DB-fetching wrappers (assertActorManageAccess, assertStorageManageAccess, assertWebhookManageAccess) are tested under production-path (no bypass) to confirm they surface DB errors.

### MINOR
- Platform events use fire-and-forget emission (void emitEvent) at all 6 call sites. If the DB insert fails (connection error, constraint violation), the rejection is an unhandled promise rejection with no retry or logging. 12 unhandled rejection warnings confirmed in test runs from schedule-runner and run-executor tests where emitEvent reaches mocked Prisma without platformEvent.create. In production with a real Prisma client the rejection is still unhandled if the DB write fails.
- PlatformEvent cursor pagination now includes secondary sort by id (createdAt desc, id desc) for stable ordering. RESOLVED.
- GET /workspaces/:workspaceId/events types query filter now normalizes to uppercase — mismatched casing no longer silently returns zero results. RESOLVED.
- No Prisma migration has been generated for the PlatformEvent model. The schema exists in prisma/schema.prisma but cannot be applied to a database without running prisma migrate dev.
- Lifecycle hook emitEvent calls are not asserted in existing run/schedule/actor tests — the fire-and-forget side effects (void emitEvent) are not verified by the test suite. Only emitEvent's unit test (5 tests) and the route-level DB-failure tests validate the helper and endpoint.
- Workspace settings slug uniqueness now enforced at the application level (409 conflict) — backed by DB-level @@unique([organizationId, slug]). RESOLVED.
- Route-level scope deny tests (token with read-only scopes attempting write route → 403) cannot be exercised at HTTP level without a running PostgreSQL instance. The requireTokenScope middleware bypasses under VITEST, and production-path tests cannot reach the middleware without a real token lookup succeeding. Scope logic (hasScope, validateScopes) is unit-tested as pure functions.
- Webhook trigger flow (triggerWebhooks) bypasses under VITEST — the full end-to-end path (webhook lookup → attempt creation → HTTP delivery → attempt status update) cannot be tested without a running PostgreSQL instance. The delivery function (deliverWebhook) is unit-tested with mocked fetch; the trigger logic (event type matching, attempt lifecycle) requires DB access.
- Webhook retry flow (finalizeAttempt → isRetriable → calculateNextRetry → DB update) cannot be fully tested without a running PostgreSQL instance. triggerWebhooks bypasses under VITEST, so the retry metadata persistence path (RETRYING/FAILED status, nextRetryAt, attemptCount) is not exercised at the integration level. Pure-function tests (25 tests) cover isRetriable and calculateNextRetry exhaustively — 17 classification scenarios and 8 delay/schedule assertions.
- Webhook retry worker (processRetryAttempts) integration test gap — the full end-to-end worker flow (DB query → claim → HTTP delivery → DB finalize) requires a running PostgreSQL instance. 14 unit tests cover selection (due RETRYING + stale DELIVERING), claim races (including stale claim skip), and outcome transitions via mocked Prisma. The stale DELIVERING claim now uses a real status transition (DELIVERING → RETRYING → DELIVERING) for mutual exclusion, tested via mock assertion — true race behavior requires a real DB and multi-process coordination. Stale recovery grace period (30s) is a static constant; its interaction with real clock skew is untested.
- Schedule runner (processDueSchedules) integration test gap — the full end-to-end worker flow (DB query → claim → actor lookup → run creation → state update) requires a running PostgreSQL instance. 13 unit tests cover computeNextRun (pure function) and processDueSchedules via mocked Prisma. True claim race behavior and cron-based time filtering require a real DB.
- Schedule runner stale recovery RESOLVED — recoverStaleSchedules() recovers orphaned schedules (nextRunAt=sentinel) on each scheduler tick with 30s grace threshold. At-least-once semantics: duplicate dispatch possible after crash recovery. True claim race behavior and integration test of recovery path require a real PostgreSQL instance.
- Run executor is now child-process isolated via child_process.fork() — each run executes in a separate Node.js process with 5-minute timeout, crash detection (non-zero exit), and spawn error handling. This provides process-level isolation (separate memory space, crash immunity) suitable for MVP. True sandboxing (Docker containers, cgroups, seccomp, resource limits) remains a future production upgrade.
- Run executor integration test gap — the full end-to-end flow (claim PENDING → execute → finalize → create dataset → write items → persist logs → trigger webhooks) requires a running PostgreSQL instance. 14 unit tests cover the logic via mocked Prisma, testing: claim success/failure, worker failure→FAILED, timeout→FAILED+kill, crash→FAILED, process error→FAILED, input.items production, double-failure resilience, cancelRun kill (running + unknown), finalize no-op after CANCELED, and concurrent cancel+success race (no artifacts).
- Concurrent cancel+success race RESOLVED: Executor success path now atomically finalizes (updateMany with status="RUNNING" filter) BEFORE creating dataset/items/logs/firing webhooks. If the row was already CANCELED (count=0), the executor logs a warning, returns { succeeded: false }, and skips all artifact creation and webhook emission. The cancel endpoint's updateMany and the executor's finalize updateMany share the same status-filter atomicity guarantee — no distributed lock required.
- PATCH /runs/:id no longer accepts CANCELED (as of 2026-07-23). Users must use POST /runs/:id/cancel to cancel runs. This ensures cancelRun(id) is always called to kill the child process on RUNNING→CANCELED transitions. The cancel endpoint enforces the same workspace membership check and scope requirement.
- Actor lifecycle migration impact: after the next `prisma migrate`, existing Actor rows receive `status = 'DRAFT'` (via @default(DRAFT)). Any previously working actors will reject new run creation until explicitly published via the transition endpoint. In MVP with no production data, this is acceptable — the migration must be documented and handled before production deployment. Options: set @default(PUBLISHED) for migration compatibility, or add a data migration step.

### INFO
- Console auth uses localStorage for token storage. Token is sent as `Authorization: Bearer` header on all API calls. On 401, token is cleared and login overlay shown. No server-side sessions. No CSRF protection on the console page itself (it's a dev/admin tool, not a user-facing app). Token expiry is enforced server-side by the `requireAuth` middleware. In dev mode (VITEST bypass), the console works without a token because the middleware bypasses auth entirely.
